# Mage-VL 复核服务迁移到 192.168.104.54 设计

日期：2026-09-15

状态：已于 2026-09-15 经用户确认

范围：只迁移防拍系统的 Mage-VL 大模型复核服务

## 背景与结论

生产检测、录像和网页服务当前运行在 50-2。Mage-VL 复核服务运行在 `192.168.104.53:8879`。2026-09-15 10:25:50，另一项 `llama-server` 工作开始同时占用旧服务器两张 GPU；Mage-VL 最后一次成功写入缓存为 10:26:25，随后生产事件从约 10:27 起连续收到 HTTP 500。实时检测保持 8/8 路在线、约 80 FPS，故障限定在 VLM 复核层。

新服务器 `192.168.104.54` 有一张空闲 RTX 3080 10GB，检查时约 9.7GB 显存可用；内存 32GB、可用约 17GB，`/home` 可用约 1.1TB。新旧大模型服务器均为 NVIDIA 570.133.07 驱动和 glibc 2.31，二者为千兆直连网络，延迟约 0.1ms。迁移可行。

## 目标

- 将 Mage-VL 推理完全迁移到 `.54` 并独占该机唯一一张 GPU。
- 用户从其他电脑访问防拍网页时，网页地址、域名、协议和对外端口全部保持不变。
- 不重启 DeepStream、GPU 检测、摄像头、MediaMTX 或录像。
- 新服务验证成功前不切换生产；切换失败时恢复原后台配置。
- 新服务稳定后，只重新排队本次 HTTP 500 造成的失败复核，不改动成功结果或人工复核结果。

## 非目标

- 不迁移网页、事件列表、检测、录像或视频下载服务。
- 不迁移对方的 `llama-server`。
- 不改变检测规则、模型阈值、摄像头配置或公网访问控制。
- 不借迁移机会升级 Mage-VL 模型、提示词、证据格式或 Python 依赖。

## 方案选择

采用 50-2 直接连接 `.54:8879`。

未采用 `.53` 透明转发：它可以避免后台配置切换，但会让旧服务器继续成为单点，不符合真正迁移的目标。未采用双端自动容灾：这需要新增客户端选择逻辑和故障判定，显著扩大本次范围；当前优先恢复稳定复核。

## 最终数据流

```text
用户浏览器
  -> 现有公网地址和现有网页端口（不变）
  -> 50-2 上现有网页/事件服务（不变）
  -> HTTPS 192.168.104.54:8879（仅此内部地址改变）
  -> 新机独占 GPU 的 Mage-VL
```

前端代码、反向代理监听端口和公开 URL 均不修改。浏览器不会直接访问 `.54`，也不需要修改收藏夹或客户端配置。

## 新服务器部署

目标目录使用 `/home/zty/YL/JianKong`，由 `zty` 用户持有。迁移以下内容：

- 当前生产 Mage-VL release，约 840KB；
- 当前 AWQ INT4 模型，约 3.9GB；
- 精确锁定的 Python 3.12.13 依赖环境；
- 新服务器专用运行目录、日志、GPU 锁、共享请求签名密钥和 TLS 服务器证书。

不复制历史成功缓存；生产侧已经持久化成功结果，失败事件在切换后定向补跑。代码、模型和环境传输使用新旧服务器之间的 `rsync`，传输前后记录清单并校验 SHA256。依赖按旧环境的精确版本重建，不使用新机 base 环境中未固定的包。

新服务绑定 `192.168.104.54:8879`，保持现有 HMAC 请求/响应签名协议、模型版本、提示词版本和证据版本。为 `.54` 签发匹配的新 TLS 服务器证书，客户端继续使用现有信任根；私钥和共享密钥不写入 Git、不输出到日志。

## 网络与切换

50-2 当前只有到 `.53/32` 的静态路由，访问 `.54` 会返回网络不可达。切换前，在 50-2 的现有 NetworkManager 连接上增加精确的 `.54/32` 持久路由，经 `192.168.0.1`，不添加整个网段路由。先验证路由、TCP、TLS、签名健康检查及真实视频复核，再修改生产 VLM endpoint。

生产切换只更新内部 VLM endpoint 和匹配证书，然后使用受控的 services-only 重载。允许约 1 分钟网页/事件服务短暂重载；外部网页端口不改变。重载过程必须核对 watchdog 的服务停止语义，并保证 MediaMTX/DeepStream 的进程身份在切换前后完全不变。

## 验证与成功条件

切换前：

1. 新服务器代码、模型和环境哈希匹配来源。
2. 新服务启动后只有其 owned PID 使用目标 GPU，健康接口的模型/提示词/证据版本完全匹配。
3. 从 50-2 对新服务执行一次真实已录制事件复核，HTTP 200、响应签名正确、结果结构合法；该探针不修改生产事件状态。
4. 旧 endpoint、配置哈希和回滚副本保留。

切换后：

1. 公网网页地址和端口不变，页面可打开，事件列表及视频播放正常。
2. 8/8 摄像头在线，约 80 FPS，MediaMTX/DeepStream PID 不变，source errors 为 0。
3. 至少 5 个新事件连续完成 VLM 复核，且 10 分钟内没有新的 HTTP 500。
4. `.54` GPU 无其他计算进程，显存和系统内存留有推理余量。

## 失败事件补跑

切换稳定后，读取 2026-09-15 当前 run 的 VLM sidecar，在权威存储锁下只选择：结果为 `error`、错误为旧服务 HTTP 500、模型/提示词/证据 revision 与当前一致的事件。操作前保存只读审计副本及 SHA256；不选择 `pass`、`filter`、`uncertain`、`pending` 或任何人工复核字段。

补跑串行进入现有 VLM worker，沿用队列限速。完成后报告重新成功、仍失败和未处理的数量。已经达到 5 次上限的记录必须通过受控的定向重排进入队列，不能依赖服务重启自动恢复。

## 回滚与旧服务退役

新服务在预切换验证失败时不修改生产。切换或观察期失败时，将 VLM endpoint 和证书恢复为备份，并只重载网页/事件服务。由于旧机 GPU 当前仍被另一任务占用，回滚到 `.53` 只有在旧 GPU 重新具备足够余量时才能恢复 VLM 推理；配置回滚本身不能解决旧机显存争用。

新服务连续稳定 10 分钟、生产验证完成且失败批次开始正常补跑后，停止旧 `.53` 的 Mage-VL 监督进程并保留其 release、模型、配置和日志，不删除数据。这样释放旧 GPU 给其他任务，同时仍保留可审计的恢复材料。

## 安全与操作约束

- 迁移凭据、TLS 私钥、共享密钥和摄像头视频不进入 Git 或终端摘要。
- 不开放新的公网端口；`.54:8879` 仅服务于内部 50-2 客户端并保留应用层签名认证。
- 所有配置写入均采用备份和原子替换，所有进程停止均核对 PID/start token/PGID/owner。
- 不清理现有生产脏修改，不回滚用户文件，不通过重启检测链路掩盖 VLM 故障。
